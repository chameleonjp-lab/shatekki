# 屋台の射的ゲーム — Claude Code 実装計画（Opus 5.5 / Sonnet 5.5）

> **実装担当のAIへ**：この計画は作業指示書であり、実装済みの証拠ではない。もし開発環境に superpowers:executing-plans 等の手順がインストールされていれば併用する。ただし、本計画に定めるClaude CodeのAgent Teams方式、ユーザーの承認権限、GitHubのPR運用を優先する。チェック欄は実行し、証拠を確認した時だけ完了にする。

**目的**：iPhone縦向け屋台射的を、確定済み33項目に沿って段階的に動かし、景品100種類・隠しセット100種類・反射や連鎖・共通画面まで完成させる。

**基本構成**：画面表現とゲームの判定を分離する。見た目・3D景品・効果音・演出はClaude側が設計する。Claude Codeが段階ごとに実装・自動確認・PR提出し、ChatGPTは要件の管理・想定外の動作の調査・不具合修正を担当する。相互の連絡はGitHubの申し送り文書とPR/Issueで行う。

**実装方式（初期提案）**：TypeScript＋Vite、WebGLによる軽量3D（Three.js候補）、衝突・物理（Rapier等を比較しiPhone Safariで先に実証）、Vitest、ブラウザE2Eテスト候補。ライブラリ採用・版・ライセンス・モバイル性能は最初の技術検証で確定し、選定結果をPRに記録する。重い物理演算と描画は切り離す。

## 0. 役割・権限・禁止事項

| 担当 | 使用モデル・役割 | 主な責任 | 権限の境界 |
|---|---|---|---|
| Claude Codeリーダー | **Opus 5.5（claude-opus-5-5）** | 開発タスクの分割・依存関係・設計審査・重要な物理/保存/採点の判断・統合テスト・PR提出・申し送り | 自分の判断で33項目やスコア計算を変更しない |
| Claude Code：Game | **Sonnet 5.5（claude-sonnet-5-5）** | 状態遷移、物理・衝突、景品耐久値、装填、反射、ギミックの実装とテスト | デザイン素材や共通UIの見た目を独断で変更しない |
| Claude Code：Visual | **Sonnet 5.5** | 店主・棚・景品・光・効果音・演出を含むビジュアルディレクション、軽量化、描画と操作の見やすさ | 採点・命中判定・持ち球・コンボのルールを変えない |
| Claude Code：UI/QA | **Sonnet 5.5** | ホーム/結果、図鑑、言語、音設定、結果共有、テスト・再現手順 | 初期は必要なタスクだけ追加起動し、同一ファイルを別担当と同時編集しない |
| ChatGPT | モデルを固定しない | 要件・仕様の整合管理、実装と要件の差異の検証、再現可能な不具合の修正、異常ケースの対策、Claudeへの修正申し送り | 明示依頼がない限り、Claudeが持つ見た目・デザインを変更しない |
| ユーザー | 最終承認者 | 要件変更、費用が生じ得る操作、DB・公開設定の変更、PRマージ、本番公開の承認 | AIが代理でマージ・破壊的変更をしない |

**実行しない操作**：main直push（初回READMEのみ例外は終了済み）、AIによる自動マージ、無断のデータ削除や再帰削除、既存ランキング/識別値/記録の初期化、未承認のDB変更・RLS/認証変更・公開変更・外部共有、秘密情報の公開、追加料金が発生し得るサービス利用の無断開始。Codex Cloudは使わない。画像生成・デザイン資産はClaude側が利用可能な手段と権利を確認して用意する。非商用・無料公開予定でも他者素材の利用許諾は別に確認する。

**費用の管理**：Agent Teamsは使用量が人数分増える。初期はリーダー1＋並行Sonnet最大2の合計3セッションを推奨し、独立した作業が明確な場合に限りSonnetのUI/QAを追加して最大4セッションまで。人数増、API従量課金、新しい外部サービスの契約、有料音源や素材の取得にはユーザーの事前確認を取る。既存契約内で利用可能かも確認する。「止められた作業」を理由に別の有料機能へ自動切替しない。

## 1. オーケストレーションの動かし方

Claude Codeの公式Agent Teamsは**実験的・初期無効**で、利用環境と版によって操作・復元動作が異なる。以下は計画であり、このPRでAgent Teamsや費用のかかる実行は有効化しない。

1. リーダーが開始時に main、開いているPR、要件、最新の申し送りを確認する。Claude Code上で使用可能なモデルを確認する。Opus 5.5とSonnet 5.5が選べない場合は別モデルへ黙って置き換えず、理由を報告する。
2. 環境が対応し、ユーザーが実際の使用を了承している場合、Agent Teamsを有効化する。公式の設定例は環境変数 **CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1**。セッションをまたぐ復元が完全ではないため、GitHubのコミット・タスク・申し送りを再開点にする。
3. Opusをリーダーとし、Sonnetの「Game」「Visual」を並列に割り当てる。「UI/QA」は基盤のインターフェースが固まった後に追加するか、Visual担当と交代で起動する。モデルをタスク指示で明示し、実際の割り当て結果を記録する。
4. 各タスクは担当、変更できるファイル、入力となる設計、成果物、確認方法、依存タスク、担当モデル、PRを持つ。互いのファイルを同時編集しない。衝突する場合は先にインターフェースを凍結してから分担する。
5. まとまった変更をPRにし、リーダーが差分・テスト・iPhone検証証跡を確認する。マージはユーザー。レビュー待ちの間は独立した資料・素材・テスト設計を進め、未マージの別PRに無断依存するコードを本線へ入れない。
6. Agent Teamsが利用できない場合は、Claude Codeのサブエージェントを使うか、独立したworktreeでSonnetの作業を順次進める。並列度より安全な統合を優先する。チームチャットは**GitHub経由のChatGPTとの申し送りの代用にはならない**。

- Worktrees: https://code.claude.com/docs/en/worktrees

## 2. 設計の境界とファイル所有（実装時の予定パス）

> 以下のパスは**将来作成する候補**。既存実装を調査し、より適切ならリーダーがPRで理由を記録して変更できる。新しい仕様を無断で追加することは許さない。

| 領域 | 予定ファイル | 主な所有者 | 外部へ公開する約束 |
|---|---|---|---|
| アプリ起点・設定 | package.json, src/main.ts, src/app.ts, vite.config.ts, CI | Opusリーダー | 各領域を接続し、バージョンや環境設定を統一 |
| 型・ルール・状態 | src/core/types.ts, state.ts, transitions.ts, scoring.ts | Game／Opus審査 | 入力コマンドと状態、ゲーム中の出来事、確定結果 |
| 衝突・景品 | src/sim/world.ts, collisions.ts, prize.ts, shot.ts | Game | 描画とは独立に、一定時間幅で処理できる |
| 候補データ・セット | src/catalog/types.ts, validate.ts, sets.ts | Game／UI/QA（書込み分割） | 100景品・100セットの参照、成立判定、未確定値検出 |
| 描画・ビジュアル | src/view/scene.ts, prizes.ts, booth.ts, effects.ts, assets/ | Visual | 確定した出来事だけを描画し、ルールへ逆流させない |
| 音響 | src/audio/ | Visual（デザイン）とUI/QA（設定）の責任ファイルを分ける | 音の再生はイベントに反応し、判定を起こさない |
| UI・図鑑・多言語 | src/ui/, src/i18n/ | UI/QA | 縦向き操作、共通画面、15言語、共有 |
| 保存・通信 | src/persistence/, src/ranking/ | Opus統合＋Game／UI/QA | 中断や再送に強い。DB変更は別承認 |
| テスト・性能 | tests/unit/, tests/integration/, tests/e2e/ | 原則各所有者。横断確認はUI/QA | 受入確認45件と証跡を対応付ける |

**予定する共有インターフェース**（Task 02で正確な型を凍結し、後続はその名前を再利用）：

    type Phase = "home" | "position" | "load" | "aim" | "flight" | "settling" | "replenish" | "result" | "interrupted";
    type GameCommand = { type: "SET_POSITION" | "STOP_LOAD" | "AIM" | "FIRE" | "SETTLE" | "RESUME" | "ABANDON"; payload?: unknown };
    type GameEvent = { id: string; shotId: string; type: string; sourceId?: string; instanceId?: string; payload?: unknown };
    type ShotSummary = { shotId: string; prizeIds: string[]; setIds: string[]; bonusShots: number; scoreDelta: number; chainCount: number };
    type GameState = { runId: string; rulesVersion: string; phase: Phase; remainingShots: number; addedShotsTotal: number; score: number; /* snapshot */ };
    function reduceGame(state: GameState, command: GameCommand): GameState;
    function resolveShot(state: GameState, events: readonly GameEvent[]): { state: GameState; summary: ShotSummary };
    function validateCatalog(data: unknown): CatalogValidationResult;

これらは開発用の設計提案で、追加のゲームルールではない。外側の描画処理はGameEventを受け取るだけで採点しない。各イベントには一意のID、元の一射ID、対象個体IDを持たせ、二重加点を防ぐ。実測心拍は取得しない。

## 3. 最初に確認すべき失敗と検査場所

| 主な失敗 | 検査するタスク | 期待する動作 |
|---|---|---|
| 最後の弾が分裂し、追加弾と複数セットが同時に成立する | 07, 08, 10 | 追加弾・獲得・セットを一度ずつ確定し、残弾に応じて続行 |
| 景品が棚から下段へ移動して補充枠を塞ぐ | 06 | 既存景品を消したり押しのけたりせず補充延期 |
| 画面外の反射や高速弾で命中が抜ける | 05, 07 | 視点に関係なく衝突を処理し、画面外でも成立した命中を可視化 |
| 発射途中の再読み込みで得点や弾数が復活する | 10 | 中断扱いにして完了ランキングへ送信せず、無料やり直しを防止 |
| 多数の演出と音、言語切替、縦画面の短い表示が重なる | 11, 14, 15, 17 | 判定値を変えず、読める表示と操作を保持し、負荷制限する |

## 4. 段階ごとの作業計画（担当・依存・PR条件）

以下の各Taskの**完了**は、成果物のコミットと実際に行った検査証跡がそろった状態を指す。テストコマンドがまだない時は、そのTaskでコマンドを追加してから判定する。仮の見た目・数値を使用した場合は「試作値」と表示し、正式完成とは扱わない。

#### Task 00 — 開始時の現状調査（Opus）
**対象**：main、開いているPR、docs全体、候補JSON、申し送り。**出力**：採用仕様チェックリスト、ライブラリ比較表、未確定値、担当ファイル一覧、実装前に必要な承認事項。

- [ ] 最新mainとPRの差分を読み、33の決定が実装条件に含まれることを確認。
- [ ] Three.js＋物理ライブラリの動作、バンドル容量、ライセンス、iPhone Safariの負荷を調査。物理実験が不成立なら原因と代案を文書化し、ゲームルールは変更しない。
- [ ] 設計上の候補を「Claude実装上の判断」「ChatGPT要件判断」「ユーザー承認事項」に分類し、必要な申し送りを作成。
- [ ] ソース・テストの所有範囲を確定し、同時編集禁止領域をチーム共有。
- [ ] 使用モデルの実態、チームが使用可能か、料金・回数の制限を記録。追加費用が必要なら稼働前に停止。

### 第2段階：反射・隠しギミック・得点

#### Task 08 — 特殊装置と店主の命中（Sonnet Game／Visualは並列で見た目）

#### Task 09 — セット100組と点数の確定（Sonnet Game／Opus承認）
**候補ファイル**：src/core/scoring.ts、src/catalog/sets.ts、tests/unit/scoring.test.ts。**依存**：03,06,08。**出力**：各射ごとの加点・減点・成立セットと、最大連鎖。

## 5. PRの並び方とレビュー条件

| 順番 | PRテーマ | 先行条件 | レビューで確認するもの |
|---|---|---|---|
| P0 | 技術選定・起動・共通契約 | Task 00 | 端末に合う構成とインターフェース、CI起動 |
| P1 | 最小射的・景品落下・補充 | P0をマージ | 撃つ→当たる→落ちる→補充→弾切れ、初期10発 |
| P2 | 仕掛け・100セット・採点・保存 | P1をマージ | 一射での二重発動防止、中断、減点、得点内訳 |
| P3 | Claudeが作る3D景品・屋台・店主・音・演出 | 最低限のGameEvent契約 | デザイン案、iPhone画像、性能、権利メモ。独立モジュールはP1/2と並行設計可能 |
| P4 | 共通画面・15言語・図鑑 | 必要な契約がマージ済み | 日本語の使いやすさと全言語のキー、結果の正しさ |
| P5 | ランキング・再送・不正対策 | 本番DB関連の明示承認 | DB移行、再送の二重記録、上位30名、実URL |
| P6 | 品質確認・公開準備 | P1〜P5統合と別途公開承認 | AC01〜AC45の記録、iPhone実機、セキュリティ、公開手順 |

テーマが大きい場合はP2a/P2bのように**独立してテストできる範囲**で分割する。毎回、担当者・変更ファイル・決定番号・確認したテスト・未確認事項・スクリーンショット・申し送り先リンクをPR本文に記す。各PRのレビュー結果を反映し、修正完了後に再テストする。ChatGPTによる不具合修正とClaudeのデザインPRが衝突する場合、契約・判定の修正を先に統合し、Claudeが見た目を整える。両方のPRを無断で相互上書きしない。

## 6. ChatGPT ↔ Claude への申し送り

相手へ渡す事項は会話だけで流さず、[申し送り規約](../../handoff/protocol.md)に従ってGitHubへ記録する。要件の変更・未定事項はChatGPT向け、ビジュアル修正・実装上の受け渡しはClaude向けに記録する。

**相手専用の別リポジトリURLはまだ提示されていない**。このため、暫定的な共通の正本を shatekki の docs/handoff/ に置き、相手宛先のフォルダで区別する。実際に別リポジトリを指定されたらその宛先へPRで移し、リンクを相互に残す。新しい外部リポジトリを無断で作成しない。

伝達の単位は1案件=1件。少なくともID、発行元、宛先、対象要件、症状・期待と実際、再現手順、証拠、影響範囲、必要な決定、PR・コミット、状態、次担当を記す。返信はGitHubのIssue/PRへのコメントまたは相手向け文書に残し、要件に影響する場合はChatGPTが決定記録更新PRを作成する。**ClaudeはChatGPTからの指摘を確認してから実装修正し、勝手に33項目を書き換えない**。ChatGPTもClaudeのビジュアル設計ファイルを独断で改変しない。
