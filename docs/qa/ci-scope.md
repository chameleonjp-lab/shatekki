# 変更範囲に合わせた自動確認

2026年11月6日。全試験を毎回繰り返す方式から、差分による選択と並行実行へ変更する。以前のPR #13のCIは約4分で、画面操作56件が約3分12秒を占めていた。速度の比較は同じ環境ではないため、予測値と実測を分ける。

## 実行する範囲

| 変更 | 確認 |
|---|---|
| README、CLAUDE、AGENTS、景品/セット候補表以外のdocs内Markdownだけ | 変更判定の自己試験と最後の確認。ゲーム試験・型検査・ビルド・ブラウザ導入は実行しない |
| ランキング | ランキング・名前・再送・結果表示・共有・安全性の対象試験、型検査・ビルド。ブラウザ全56件は繰り返さない |
| 言語・ホームや結果画面・音 | 関係する単体・統合試験と必要な画面試験、型検査・ビルド |
| 試験ファイルだけ | 変更した試験を実行。画面試験ならビルドも作る。補助ファイルや削除は全試験へ戻す |
| 採点・物理・保存・共有型・起点・候補データ・景品/セット候補表・依存関係・設定・CI自身・分類できない変更 | 全試験。比較元が不明・無効な場合も全試験へ戻す |

複数分類の変更では確認範囲を合算する。改名は移動元と移動先の両方を調べる。削除した試験が「対象0件だから成功」となることは認めない。対象の実装は `scripts/ci/plan.mjs`、選択した試験の実行は `scripts/ci/run-tests.mjs` にまとめる。

対象試験が選択されなかった場合の意図した省略と、起動した試験が0件だった場合を区別する。Vitestの試験0件・skip/todo検査は既存のラッパーを引き続き使い、分割したPlaywrightでは0件が成功になる場合があるため、実行前に古いレポートだけを除き、実行後の新しいJSONで成功件数が1件以上、失敗・skip・flakyが0件であることを確認する。レポート欠落も失敗にする。

全ての実行コードの変更では、秘密情報がsrcや配信物へ混ざっていないかを確認する既存の安全性試験も選ぶ。この試験には専用の短いビルドが残る。画面試験ごとのビルドは省くが、この検査まで取り去ったわけではない。

## 並行実行と重複の削減

Node上の試験と、型検査・ビルドを並行して動かす。画面試験は2台に分割し、各台の実行数を2に抑える。どちらも同じCI実行のビルド成果物 `site-dist` を使うため、画面試験側で再ビルドしない。各試験は独立したブラウザ環境を使い、同じ保存データを共有しない。

成功をまとめるジョブ名は以前と同じ `test` に保つ。文書だけの変更でもこの確認は起動するため、必須チェックが出ないまま止まらない。必要なジョブが失敗・中止・想定外の省略になった場合は最後も失敗する。選ばなかったジョブはskippedであることまで検査する。判定した範囲と理由はActionsのSummaryに残す。

古い実行は新しい変更が来たら取り消す。異なるプルリクエスト同士は取り消さない。失敗した試験だけの再実行はGitHubのRe-run failed jobsを使える。

## 画面試験の準備と試験の時間を分ける（2026年11月7日、計画T0）

PR #19のマージ後の実行 [42260041719](https://github.com/chameleonjp-lab/shatekki/actions/runs/42260041719) では、画面試験1組目が失敗ではなく中断で終わった。記録を読むと、`npx playwright install --with-deps chromium` がフォント9件（21.1 MB）をUbuntuの配布元から毎秒38.5 KBで取得し、9分7秒かかっていた。ブラウザ本体の取得は約7秒だった。試験は17時26分14秒に始まり、3件が成功した32秒後に、ジョブ全体の10分の上限で止まった。店主の質問の試験は中断前に通っている。

そこで画面試験のジョブを、ロックファイルと同じ版のPlaywright公式の実行環境 `mcr.microsoft.com/playwright:v1.63.0-noble` の中で動かすように変えた。この環境の作り方は公式リポジトリのv1.63.0の `utils/docker/Dockerfile.noble` で確かめた。作成時に `playwright-core install-deps` で依存を入れ、Chromiumを `/ms-playwright` に置いている。手元の `playwright-core` 1.63.0が持つUbuntu 24.04向けの依存一覧には、日本語の `fonts-ipafont-gothic`、中国語の `fonts-wqy-zenhei`、タイ語の `fonts-tlwg-loma-otf` が入っている。実行中にブラウザやフォントを取りにいかないので、配布元の速さに左右されない。

| 区間 | 上限 | 中身 |
|---|---|---|
| 依存パッケージ | 5分 | `npm ci` |
| 環境の確認 | 2分 | `npx playwright --version` がロックファイルの版と一致し、上の3つのフォントが入っていることを確かめる |
| 画面試験 | 12分 | 選ばれた画面試験。以前の10分より長くし、準備の時間とは分けた |
| ジョブ全体 | 20分 | 実行環境の取得と上の3区間の合計の上限 |

ロックファイルのPlaywrightを上げるときは、実行環境の版も同時に上げる。`tests/ci/browser-env.test.mjs` が版のずれ、実行中のブラウザ取得や `apt install`、確認と試験の順と上限を検査するため、片方だけ変えるとCIの自己試験で止まる。

この変更を入れたPR #21の最初の実行 [42278132035](https://github.com/chameleonjp-lab/shatekki/actions/runs/42278132035)（コミット `02a52ea`、CI自身の変更なので全試験）で、各段階の時間を測った。最後の判定 `test` まで成功している。

| 段階 | 1組目 | 2組目 |
|---|---:|---:|
| 実行環境の取得（Initialize containers） | 36秒 | 32秒 |
| `npm ci` | 3秒 | 2秒 |
| 版とフォントの確認 | 2秒 | 1秒 |
| 画面試験 | 1分55秒 | 1分24秒 |
| ジョブ全体 | 2分47秒 | 2分11秒 |

準備にかかる時間は1分未満になり、試験の時間とは別の段階として記録に残る。一度の実行で測った値なので、配布元の混み具合で変わることはありうる。

### 配信を確かめる手順

配信は、mainへのpushで動いた `ci` が最後の `test` まで成功し、同じ実行の `site-dist` があるときにだけ `pages` が行う。文書だけの変更ではビルドを省くので、配信も起きない。PR #20のマージ後の実行45はこの場合で、`pages` の実行6はビルドがないことを記録して配信していない。

このため、PR #19の版はまだ配信されていない可能性が高い。ただし公開面を直接開いて確かめてはいないので、どの版が出ているかはわからない。このCI変更はCI自身の変更なので、マージ後のmainで全試験とビルドが動き、成功すれば同じ実行の成果物が配信される。そのときに、その実行のビルドと最後の判定が成功したこと、`site-dist` の成果物番号、`pages` の配信結果、公開面が9枠であることを同じ実行の記録で突き合わせる。失敗した組だけを再実行した記録や、内部用の成果物 `internal-expanded-dist` は配信の証拠に数えない。

## 全試験を選び直す場合

Actions → ci → Run workflowでfullを指定する。依存変更や中心部分の修正では自動で全試験になる。分類表が正しいか判断できない新しい変更も、自動で全試験へ戻す。今回のCI変更自体は、この全体確認を一度通してから提出を完了する。

手元でも最初に不具合を再現する試験、修正後にその試験と影響先を実行する。同じ差分で成功した試験を理由なく繰り返さない。全試験を一度通した後は、追加の変更・失敗・未確認の懸念がない限り再実行しない。

## 公開との関係

このCIは試験のみで、Pagesやデータベースへ書き込まない。[公開設定案](../release/preview-pages.yml.example)は、後に公開を有効にする際に、成功した同じmainの成果物を再利用する。そこでも再ビルド・全試験を重複させない。

## 根拠

GitHub公式の[ジョブの依存と条件](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)と[必須チェックと省略](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)、既存Vitest 4の[ファイル指定](https://v4.vitest.dev/guide/cli)を確認した。対応関係を明示し、分類できない場合は全試験へ戻す設計はこのリポジトリでの選択である。
