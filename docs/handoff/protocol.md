# ChatGPT・Claude 間のGitHub申し送り規約

**用途**：ゲームの要件・仕様・不具合調査を担当するChatGPTと、見た目・演出・音のデザインと実装を担当するClaude Codeが、相手の会話を知らなくても仕事を引き継げるようにする。

## 1. 宛先と保存先

- このゲームの正本は **chameleonjp-lab/shatekki** の main にある[要件仕様書](../requirements.md)と[決定記録](../decision-log.md)。
- 相手向けの**別リポジトリのURLは未指定**。追加の許可があるまでは本リポジトリの **docs/handoff/to-claude/** と **docs/handoff/to-chatgpt/** を暫定窓口とする。各窓口に案件別Markdownを作成し、作業ブランチからPRを提出する。
- 対象の別リポジトリが明示されたら、ユーザーが指定した相手側リポジトリの同名ディレクトリに送信する。双方にissue/PRへの相互リンクを残す。認証・アクセス権のないリポジトリへ書き込んだと主張しない。
- 申送り内容のうち、要件として確定した変更は、ChatGPTが要件書と決定記録へPRで反映し、ユーザーがマージしてから有効とする。

## 2. 変更の責任境界

| 種類 | 記入する側 | 判断・作業する側 | 原則 |
|---|---|---|---|
| 仕様の不明点、ルール矛盾 | Claude → ChatGPT | ChatGPTが根拠を確認。必要ならユーザーへ確認 | Claudeは未決定事項を実装済み仕様へ変えない |
| 動作の不具合、予期しない得点 | Claude → ChatGPT | ChatGPTが再現・修正・検証、Claudeが必要に応じて描画側追従 | 原因が見た目か判定かを分ける |
| ビジュアル・3D素材・演出・音 | ChatGPT → Claude | Claudeが設計・変更・実機確認 | ChatGPTは見た目を独自に作り直さない |
| 型・イベント・ファイル境界の変更 | 変更提案者 → 相手 | 双方が依存範囲を確認し、Opusが統合調整 | 変更対象の事前共有がないまま同じファイルを編集しない |
| 本番DB・権限・公開・費用 | どちらでも起案可 | **ユーザーの明示承認** | 「前回許可された」を流用しない |

## 3. 案件1件の書式

ファイル名案：YYYY-MM-DD-HHMM-短い識別名.md（同名を上書きせず新しいIssue/PRへ紐付ける）

~~~markdown
# HANDOFF: 何を引き継ぐか
- ID: SHK-YYYYMMDD-001
- 発信: Claude（またはChatGPT）
- 宛先: ChatGPT（またはClaude）
- 種別: 仕様確認 / 不具合 / デザイン / 依存変更 / 承認
- 状態: NEW / ACK / WORKING / FIXED / VERIFIED / BLOCKED / CLOSED
- 重要度: P0停止 / P1主要 / P2軽微
- 対象要件: 例）決定31、AC16
- リポジトリ: chameleonjp-lab/shatekki
- 参照: ブランチ、PR、コミットSHA、関係ファイルと行
- 期待する結果:
- 実際に起きたこと:
- 再現手順: 端末、画面向き、残弾、景品、当たり位置、操作順
- 証拠: スクリーンショット、動画、テストログ、再現用seed（機密情報は載せない）
- 疑っている原因: 未検証の仮説として書く
- 影響: ゲーム判定 / 見た目 / 保存 / ランキング / 他のPR
- 依頼する決定・修正:
- やってはいけないこと:
- 返信先: Issue / PR / 当該ファイル
- 次担当:
- 期限: 必要な場合のみ。未確定なら「なし」
~~~

相手からの返信には、元のID、判断の根拠、採用/不採用の理由、修正PR、検証証拠、引き継ぐ担当と次の状態を明記する。**「修正済み」「検証済み」はPRやテスト結果のURL・コミットが確認できた時だけ**使う。

## 4. 不具合の優先順位と滞留防止

- **P0**：データ消失・秘密情報露出・ランキング誤登録・再現可能な無限得点・ゲーム進行不能。関連箇所の統合・公開を止める。原因未確定でも他の独立作業へ振り分ける。
- **P1**：主要操作が使えない、落下と得点が不一致、iPhone縦表示欠け、音設定無視。再現テストと修正PRを優先する。
- **P2**：小さな演出ずれ、軽微な説明不足。デザイン担当へ具体的な動画・画面を添えて送る。

プルリクエストのレビュー待ち、未決定の要件、サービス権限不足では無断で作業を進めない。ただし、衝突しない別の仕事（テスト設計・素材・説明文・不具合の再現検証）は進める。これを「承認なしの破壊的変更」の例外としない。

## 5. GitHubの競合・追跡・承認

1. 誰かが同じモジュールを変更する前に、担当・所有パス・元のmain SHAと進行中PRを確認する。
2. 修正PRには「要件のどの番号に対応するか」「テストがどれか」「どの画面・音に影響するか」を書く。
3. 仕様が変わる案件はChatGPTの判断を待つ。Claudeは並行して別の視覚表現の作成などを進められる。
4. 仕様修正PRがマージされてからClaudeはそのmainを取り込み、デザイン側の互換を確認する。
5. レビュー・マージはユーザー。AI側で自動マージ・main直pushはしない。DB・公開・費用には別の承認が必要。

## 6. 最初に作る窓口

- **docs/handoff/to-chatgpt/**：Claudeが、要件確認や不具合をChatGPTへ渡すための保管場所。
- **docs/handoff/to-claude/**：ChatGPTが、確定仕様や修正後の変更、ビジュアル担当への依頼をClaudeへ渡す保管場所。

作成時点では、この規約と窓口の説明だけを用意する。具体的な不具合・完了を事実に反して書き込まない。
