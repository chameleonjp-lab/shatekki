# ChatGPT・Claude 間の申し送り規約（敵対的検証反映版）

2026-11-06／1.1。正本は[要件](../requirements.md)と[決定記録](../decision-log.md)。[実装計画](../superpowers/plans/2026-11-06-shatekki-claude-code.md)と[検証結果](../reviews/2026-11-06-plan-adversarial-review.md)も参照する。

## 宛先・受領・仕様の採用を分ける

相手用の別リポジトリは未指定。暫定的に `chameleonjp-lab/shatekki` の `docs/handoff/to-chatgpt/`、`docs/handoff/to-claude/` を使う。別repoが指定されたら所有者/名前/権限/対象ブランチを確認して、その受信先へPRまたは既存の連絡Issueを使って記録する。無断で新しいrepoを作成しない。移す際も元記録を消さず、同じ案件IDと双方向のリンクを残す。

メモ作成、GitHub送信成功、相手の受領、仕様の承認、mainへのマージは別の状態。メモだけで相手のAIが自動起動・受領したと主張しない。実行セッションの開始時、担当取得前、PR提出前に自分宛の新着/未解決メモを読む。定期監視やバックグラウンド実行をこの文書だけで開始しない。

未マージのメモやPRでも相手は参照・質問・回答できる。回答待ちを理由にメモのマージまで全作業を止めない。ただし、未承認の仕様変更を実装へ採用しない。最新の明示的な利用者決定があればその根拠を記録し、正本へ反映する。ChatGPTの判断だけで新しいゲームルールを承認しない。

## 所有と修正の境界

| 事項 | 担当と手順 |
|---|---|
| 初期実装の失敗テスト・書きかけのコード | Claudeの担当が直し、自分のTaskの試験を通す。毎回ChatGPT待ちにしない |
| 統合済みの判定・保存・採点などの不具合/想定外 | Claudeが再現・根拠を添えてChatGPTへ。ChatGPTが修正担当、Opusが所有パスと統合順を調整 |
| 美術・演出・音のデザイン、不具合に伴う見た目の調整 | Claude。ChatGPTは必要条件と症状を渡し、独自の美術判断で作り直さない |
| 契約型・イベント・呼出し順の変更 | 提案側が影響先を列挙し、Opusが共有型を単独編集。相手の参照SHAを更新 |
| 明確な既存仕様への復帰修正 | 新しい遊びの承認とは別。回帰テストと修正PRで提出 |
| 仕様変更・追加機能・点数の正式化 | ChatGPTが根拠と案を整理し、利用者の決定を受け正本更新PRへ |
| DB/権限/費用/外部公開・破壊的変更 | 対象・影響・復元手順と利用者の明示承認が必要 |

ChatGPTが修正するファイルは、開始前にCLAUDE側の同パス編集を一時停止する。描画ファイルに安全修正が必要なら最小差分に留め、前後の画像と意図をClaudeへ渡す。相手の未コミット変更を上書きしない。合意した単独所有と別作業場所を使い、mainへの直接書込み・AIのマージはしない。

## 案件の書式

1件1ファイル。名前は `YYYY-MM-DD-HHMM-発信者-短い名前.md`。案件IDは発信者を含めて衝突を防ぎ、重複投稿時も元IDを維持する。

```text
ID: SHK-20261106-CHATGPT-001
発信/宛先:
種別: 仕様確認 / 不具合 / デザイン / 依存変更 / 承認
重要度: P0 / P1 / P2
配送状態: LOCAL / POSTED / ACK
作業状態: OPEN / WORKING / FIX_PROPOSED / VERIFIED / CLOSED / BLOCKED
送信先repo・PR/Issue URL:
基準main SHA・対象branch・commit・ファイル:
対象決定/AC:
期待/実際:
再現手順・端末・向き・rulesVersion・seed:
証拠URL・ログ（秘密/個人情報は除く）:
依頼する判断・変更、変更しない範囲:
担当/所有パス/次担当:
必要な利用者承認の有無と記録:
返信先:
```

受信者がACKと読んだSHAを記録する。更新返信は元ID、根拠、修正PR/commit、試験結果、相手が取る操作を含める。未マージ修正はFIX_PROPOSEDであり、main修正済みと書かない。VERIFIEDには検証対象SHAと証拠が必要。マージ後に最新mainで再確認してCLOSEDへ進める。メモを削除せず、誰が何を判断したかを追えるようにする。

## 優先度と滞留

P0はデータ消失、秘密漏えい、無限得点、重大誤登録、進行不能。該当箇所の統合/公開を止める。P1は主要操作・採点・保存・縦表示・音設定の不整合。P2は小さな表示/演出の問題。重要度はGameとVisualで原因を切り分けるためのもので、美術変更の勝手な承認ではない。

待機が必要なのは影響する箇所だけ。別担当の素材、テスト、調査など独立作業を進める。相手が返答しないことを承認と扱わない。チーム内Opusの計画承認、メモのACK、利用者の仕様/費用/公開承認を混同しない。
